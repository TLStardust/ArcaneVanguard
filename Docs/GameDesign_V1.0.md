# 1. 项目概述

## 1.1 项目愿景

Arcane Vanguard 是一款第三人称奇幻魔法战斗  
Demo。玩家扮演一名掌握奥术力量的先锋法师，在小型遗迹战场中使用远程奥术攻击与主动技能对抗敌人，并通过完成战斗目标推进任务。

项目不是以内容规模取胜，而是用一个可重复游玩的战斗场景，展示一套清晰、可维护、可测试的  
Unreal Engine 开发方案。

项目需要同时满足三个目标：

1. **可玩性：** 玩家能移动、瞄准、攻击、释放技能、击败敌人并完成目标。
2. **技术展示：** 展示 C++  
   与蓝图分工、GAS、角色与敌人框架、动画与特效、UI、任务系统接口和工程化开发习惯。
3. **可解释性：**  
   项目负责人能够解释关键架构决策、数据流、关键类职责、测试结果与已知限制，而不只是展示  
   Agent 生成的代码。

## 1.2 项目设计原则

- **先闭环，再扩展：**  
  先完成一场最小可玩战斗，再增加技能、敌人和任务内容。
- **先验证，再抽象：** 不为尚未出现的需求提前构建大型框架。
- **C++ 管规则，蓝图管组合：** 关键状态、核心规则与可测试逻辑优先放在  
  C++；资产引用、数值配置、动画和特效组合优先使用蓝图与数据资产。
- **GAS 负责能力与效果，不负责整个游戏：** 任务、UI、AI 和交互可以与  
  GAS 协作，但不应全部塞进 Ability 类。
- **接口优先、依赖单向：**  
  战斗系统向任务系统报告已发生的玩法事实；任务系统不反向控制敌人的死亡或伤害结算。
- **每次改动可审查、可回滚：** Agent  
  必须提供修改摘要、风险说明、验证命令或步骤和测试结果。
- **不以代码量衡量进度：** 以可复现的验收结果衡量进度。
- **资产合规：**  
  使用的模型、动画、音效、材质与插件必须记录来源、许可证和使用限制。

## 1.3 目标玩家与体验

- **目标体验：** 操作简单、反馈明确、节奏紧凑的第三人称魔法战斗。
- **核心体验循环：** 探索战斗区域 → 发现敌人 → 使用普通攻击与技能战斗  
  → 击败敌人 → 更新任务进度 → 完成目标。
- **镜头：** 第三人称跟随镜头。
- **战斗风格：** 远程奥术弹道、范围爆发、控制技能与终极技能组合。
- **美术方向：**  
  可读性优先的奇幻遗迹风格；奥术能量以蓝紫色为主，冰霜控制使用冷白与浅蓝，敌人攻击用明显但不刺眼的对比色。
- **音效方向：**  
  普通攻击短促、技能有层次、命中反馈清晰、冷却与资源不足反馈可辨认。

## 1.4 明确不做的内容

V1.0 不包含以下范围，除非后续经项目负责人批准并形成新版本变更记录：

- 联机、多人、服务器权威同步。
- 开放世界、复杂剧情、过场动画和完整配音。
- 大量英雄、职业、装备、天赋树、掉落和经济系统。
- 完整存档系统或跨版本存档迁移。
- 复杂行为树、多阵营战术、动态导航系统。
- 自研通用 GAS 替代框架。
- 为"架构完整"而开发的过度泛化插件体系。
- 未经验证就把现有旧项目整体迁移到新项目。
- 以大规模购买素材代替可玩的核心体验。

# 2. 项目范围与成功标准

## 2.1 V1.0 可玩 Demo 范围

首个可玩版本至少具备：

- 一个可操作的第三人称玩家角色。
- 一个小型战斗地图。
- 一种完整敌人类型；第二种敌人作为可选扩展。
- 普通奥术攻击。
- 两个主动技能与一个终极技能。
- 玩家和敌人的生命值；玩家具备法力资源。
- 技能消耗、冷却、伤害、控制与死亡流程。
- 最基本的敌人感知、追击、攻击与死亡行为。
- 生命值、法力值、技能冷却或可用状态的 UI。
- 一项可完成的任务，至少包含击杀目标；区域目标或交互目标可以作为第二阶段内容。
- 关键战斗反馈：动画、命中特效、施法特效、音效中的最低可用组合。
- 自动化或可重复的手动测试清单。
- 可从干净工作区构建、启动和演示的项目版本。
- 项目架构说明、运行说明、已知问题清单和演示视频。

## 2.2 验收指标

项目通过 V1.0 验收需满足：

1. 工程可在约定的 UE 版本与开发环境中打开、编译和运行。
2. 玩家移动、镜头、普通攻击与技能输入稳定可用。
3. GAS 属性与效果变化符合设计，资源不足和冷却期间不能违规施放。
4. 敌人能受到伤害、进入死亡流程，且同一次死亡不会重复结算。
5. 任务进度只在正确条件下更新，重复调用不会无意中重复计数。
6. UI 显示与游戏实际状态一致。
7. 关键功能有测试证据；未通过项明确标记，不得伪报通过。
8. 项目不存在已知且阻断主流程的崩溃、编译错误或严重逻辑缺陷。
9. 关键资产有来源与许可记录。
10. 项目负责人能讲清主要类职责、战斗数据流、任务接口和至少几个关键技术取舍。

## 2.3 质量优先级

发生时间冲突时按以下优先级取舍：

1. 正确性与稳定性
2. 核心战斗闭环
3. 架构可解释性与可维护性
4. 可读的视觉和音效反馈
5. 次要功能与内容数量
6. 非必要的复杂优化

# 3. 游戏设计

## 3.1 玩家角色

### 角色定位

玩家是一名擅长中远距离奥术攻击的法师。角色初期不需要复杂装备或成长系统，重点是移动、瞄准、技能释放和资源管理。

### 基础操作建议

输入                    行为             备注

---

WASD / 左摇杆           移动             使用 Enhanced Input  
鼠标 / 右摇杆           控制镜头         沿用第三人称模板基础方案  
Space / 对应手柄键      跳跃             初版沿用模板行为  
鼠标左键 / 对应手柄键   普通奥术攻击     可配置为 Ability  
Q                       奥术震荡         主动技能  
E                       霜缚             控制技能  
R                       星陨             终极技能  
Esc                     暂停或打开菜单   可在后续阶段实现

具体键位必须在输入映射资产中配置，不要把键位硬编码在战斗逻辑类里。

## 3.2 战斗循环

1. 玩家进入战斗区域。
2. 敌人发现玩家或进入警戒状态。
3. 玩家用普通攻击试探并积累技能释放节奏。
4. 玩家依据敌人距离、数量和状态选择技能。
5. 敌人受到伤害或控制，触发受击、死亡等反馈。
6. 敌人死亡后由唯一、可追踪的死亡结算入口上报击杀事实。
7. 任务系统匹配对应目标并更新进度。
8. 任务完成后显示结果或允许继续游玩。

## 3.3 技能设计

技能数值为首轮调试建议，不是最终平衡承诺。所有数值应尽可能由可配置数据资产或适当的配置对象管理，不要散落在多个  
C++ 函数里。

### 普通攻击：Arcane Bolt（奥术弹）

- **类型：** 单体远程攻击。
- **输入：** 鼠标左键。
- **效果：** 向目标方向发射奥术弹，命中后造成伤害。
- **资源：** 初版可不消耗法力，或使用极低成本；最终选项由试玩后决定。
- **冷却：** 使用轻量攻击间隔或 Ability Cooldown  
  方案，避免按住按键时无限制触发。
- **表现：** 施法动作、弹体特效、命中闪光和轻量音效。
- **验收：**  
  弹体方向正确；碰撞规则明确；单次命中只造成一次伤害；不会穿透不允许穿透的目标。

### Q：Arcane Shock（奥术震荡）

- **类型：** 短距离范围爆发。
- **效果：** 对玩家前方或目标点附近的敌人造成伤害。
- **资源：** 消耗法力。
- **冷却：** 中等冷却。
- **表现：** 明确的施法起手、范围指示或爆发效果。
- **验收：**  
  范围与伤害规则明确；每个目标在一次技能结算中不会被重复命中；资源不足时拒绝施放并给出反馈。

### E：Frost Prison（霜缚）

- **类型：** 单体或小范围控制。
- **效果：** 暂时限制敌人的移动或攻击能力，并可附带少量伤害。
- **资源：** 消耗法力。
- **冷却：** 较长于普通攻击。
- **实现建议：** 用 Gameplay Tag 表示受控状态；根据敌人  
  AI、移动和攻击系统选择合适的控制方式；明确控制结束条件。
- **验收：**  
  控制开始与结束都可验证；死亡、重复施加、控制免疫或效果移除时不会留下永久控制状态。

### R：Starfall（星陨）

- **类型：** 高成本范围终极技能。
- **效果：**  
  在指定区域或玩家前方落下奥术能量，对范围内敌人造成高额伤害。
- **资源：** 高法力消耗。
- **冷却：** 长冷却。
- **表现：** 施法蓄力、落点提示或预警、冲击特效与音效。
- **验收：**  
  伤害区域与视觉区域大体一致；冷却和资源消耗只发生一次；死亡或取消时的行为符合设计。

### 技能设计共通要求

- 输入触发、资源检查、冷却、效果应用与视觉反馈应有清晰职责分层。
- 不应仅凭播放动画就认定技能成功命中。
- 动画 Notify  
  可用于表现时序或触发经设计的动作节点，但必须防止重复触发伤害。
- 技能中断、角色死亡、目标死亡、资源不足等边界情况必须有明确行为。
- 所有关键 Gameplay Tag 统一命名并记录在标签表中。
- 对于多人游戏未纳入 V1.0 的事实，不要提前引入复杂网络预测和服务器 RPC  
  方案；但也不要把当前代码描述成已经支持联机。

## 3.5 敌人设计

### 基础敌人：Arcane Guard（奥术守卫）

行为状态建议：

- **Idle：** 未发现玩家时待机。
- **Alert：** 发现玩家，准备进入战斗。
- **Chase：** 玩家超出攻击距离时追击。
- **Attack：** 玩家进入攻击范围时尝试攻击。
- **Stunned / Frozen：** 受到控制效果时限制正常行为。
- **Dead：** 停止战斗行为，执行一次死亡结算并播放死亡表现。

不要求第一版实现复杂行为树。可使用 UE AI Controller、AI  
Perception、简单状态逻辑或行为树，选择取决于实际复杂度。不能为了展示某项技术而引入不必要的系统。

### 敌人验收

- 可被玩家发现、攻击并击败。
- 受到伤害时正确更新属性。
- 死亡后停止移动、攻击和重复伤害结算。
- 死亡流程只执行一次。
- 死亡信息能正确传递给任务系统。
- 控制效果结束后行为能够恢复；死亡敌人不能恢复正常战斗行为。

## 3.6 地图与关卡

首张地图为小型奥术遗迹战场，目标是快速进入战斗，而非打造完整开放区域。

建议区域：

1. **入口区：** 玩家生成、基础操作空间。
2. **战斗区：** 1--3 个敌人可以被玩家逐个或集中处理。
3. **目标区：** 放置任务目标点、遗迹核心或可交互物。
4. **边界区：** 明确不可通行区域，避免玩家或 AI 掉出地图。

地图设计要求：

- 玩家、敌人和技能效果的视觉轮廓可辨识。
- 地形不会频繁遮挡弹体或造成 AI 无法到达。
- 有足够空间展示范围技能与敌人追击。
- 使用简单碰撞和导航设置，避免无意义的美术细节阻断玩法。
- 先用灰盒验证空间，再进行美术布置。

## 3.7 任务与交互设计

### 第一项任务：清理奥术遗迹

- 目标一：击败 3 名奥术守卫。
- 目标二：到达遗迹核心区域（可选，视第一版时间决定）。
- 完成条件：所有必需目标完成。
- 反馈：目标计数更新、完成提示。

### 任务插件接入原则

项目已有任务插件的核心类已完成，但部分功能尚未验证。因此：

1. 先单独检查插件接口、数据结构、模块依赖与测试覆盖。
2. 用最小测试场景验证任务激活、目标匹配、进度上报、完成状态和重复上报边界。
3. 插件验证通过后，再接入 Arcane Vanguard。
4. 不在插件未验证时让 Agent 大规模重写插件。
5. 插件应保持独立，不直接依赖玩家角色、敌人蓝图或具体技能类。

### 主动上报模型

游戏系统在事实发生的业务节点调用任务插件接口。例如：

- 敌人正式死亡后：上报一次"敌人被击败"事实。
- 玩家正式进入目标区域后：上报区域到达事实。
- 交互成功完成后：上报交互完成事实。

任务插件不必主动监听所有游戏对象。游戏玩法负责确定事实发生的时机，任务插件负责目标匹配与进度管理。

### 必须明确的进度语义

- **增量上报：** 表示某个事实发生一次，例如"击杀  
  +1"。调用方必须确保单次事实不会重复上报。
- **绝对进度同步：**  
  表示把当前进度设置为某个值，不应被实现为简单累加。
- 任务目标必须有稳定标识，不能只靠显示名称匹配。
- 多个任务或目标同时有效时，必须明确一条上报会推进哪些目标。
- 任务已完成、失败、取消或未激活时收到上报，必须有确定规则。
- 重要事实应尽可能包含足够的上下文，例如目标类型、目标  
  ID、来源对象或标签；具体参数取决于插件现有接口。
- 对同一敌人死亡的重复调用应有防重机制，至少在敌人死亡入口保证一次；如插件业务需要，也可使用唯一事件  
  ID 进一步防重。

### 与 GAS 的边界

- GAS 处理属性、伤害、治疗、资源消耗、冷却、能力状态与 Gameplay Tag。
- 敌人死亡逻辑确认死亡并执行唯一的死亡结算入口。
- 任务系统接收"敌人已被击败"等玩法事实并更新目标。
- UI 展示任务状态，不负责决定任务进度。
- 任务系统不应自行扣除敌人生命值或判定战斗伤害。

# 4. 技术架构

## 4.1 总体架构

建议按职责划分为以下层次：

1. **Framework 层：**  
   GameMode、GameState（如需要）、PlayerController、PlayerState、Character  
   的职责分配。
2. **Character 层：** 玩家角色、敌人角色、移动、动画状态与生命状态。
3. **AbilitySystem 层：**  
   AbilitySystemComponent、AttributeSet、GameplayAbility、GameplayEffect、GameplayTag、GameplayCue。
4. **Combat 层：** 攻击判定、弹体、目标选择、伤害请求与死亡结算边界。
5. **AI 层：** AI Controller、感知、追击、攻击决策。
6. **UI 层：** HUD、属性显示、技能状态、任务目标展示。
7. **Task Integration 层：** Arcane Vanguard  
   与独立任务插件之间的薄适配层。
8. **Data / Assets 层：** 数据资产、动画、特效、音效、材质、输入映射。
9. **Test 层：** 自动化测试、开发测试地图、验证说明。

层次是职责划分，不要求每层都创建一个庞大模块。只在实际需要时新增模块。

## 4.2 C++ 与 Blueprint 分工

### 优先使用 C++

- 需要可靠状态约束的规则。
- 属性与效果应用逻辑。
- 死亡结算和防重逻辑。
- 可复用的组件和基础类。
- 对接口、生命周期和错误处理有要求的功能。
- 任务插件的适配层与参数校验。
- 自动化测试所需的可验证逻辑。

### 优先使用 Blueprint / Data Assets

- 资产引用与角色装配。
- 动画蓝图、Montage、Notify 配置。
- Niagara 与 Gameplay Cue 的表现组合。
- 技能数值、音效、特效、图标等可调数据。
- UMG 布局。
- 小型关卡布置和简单场景交互。
- 在不改变核心规则的前提下组合已有组件。

### 避免的做法

- 所有玩法都写进一个巨大 Character 类。
- 每个技能复制一套独立伤害与冷却逻辑。
- 把全部规则放在蓝图 Event Graph 中且无法单元验证。
- 只为"看起来高级"而把所有简单行为都改成复杂框架。
- 在多个类里各自维护同一属性的权威数值。
- C++ 与蓝图同时对同一状态进行无约束写入。

## 4.3 GAS 设计基线

### Ability System Component

- 明确 ASC 所属对象与 Actor Info 初始化时机。
- 角色、PlayerState 与 ASC 的归属方式必须结合单机需求和引擎版本确定。
- 玩家和敌人初始化 ASC 的路径要可追踪。
- 避免在多个生命周期回调中重复授予能力或重复初始化。

### AttributeSet

- 只放置确实需要 GAS 属性机制的属性。
- 约定属性变化、上限约束、伤害执行与死亡判定的位置。
- 处理当前值与最大值变化时的一致性。
- 避免让 UI、技能和敌人逻辑各自修改同一属性。

### Gameplay Ability

- 一项能力负责一项明确的玩法意图。
- 资源消耗与冷却应使用一致的策略。
- 对取消、失败、目标无效和角色死亡等情况有清晰处理。
- Ability 的生命周期必须正确结束，不留下持续运行的任务或计时行为。
- 视觉表现与规则结算应有明确边界。

### Gameplay Effect

- 用于伤害、治疗、资源变化、属性修正、冷却或持续状态等适合的效果。
- 选择 Instant、Duration、Infinite 等策略时说明原因。
- 对可叠加效果定义叠加规则。
- 不为每个数字变化都创建不必要的复杂效果链。

### Gameplay Tag

建议采用分层命名，例如：

- `State.Dead`
- `State.Controlled`
- `State.Frozen`
- `Ability.Attack.Basic`
- `Ability.Skill.ArcaneShock`
- `Ability.Skill.FrostPrison`
- `Ability.Ultimate.Starfall`
- `Event.Combat.Damage`
- `Event.Combat.Death`
- `Event.Task.Progress`
- `Cooldown.Skill.ArcaneShock`
- `Cooldown.Skill.FrostPrison`
- `Cooldown.Ultimate.Starfall`

以上只是命名建议。最终标签必须检查项目现有标签配置、GAS  
版本支持方式和实际使用点，避免重复或拼写不一致。

## 4.4 输入系统


- 优先使用 Enhanced Input。
- 输入映射与按键配置放在资产中。
- 输入层表达玩家意图；技能规则仍由 Ability 或对应玩法逻辑负责。
- 输入绑定初始化应只有明确的入口，避免重复绑定。
- 输入被 UI 捕获、角色死亡或游戏暂停时的行为应明确。
- 不把输入按键直接写进技能伤害计算代码。

## 4.5 动画与表现

- 使用第三人称模板角色或兼容的免费角色资源作为初始基线。
- 先确保骨架、动画重定向、动画蓝图和蒙太奇可用，再批量导入更多资源。
- 施法动画、命中反馈、死亡动画优先于复杂连招。
- Notify 用于动画时序与表现触发时，必须评估重复触发、取消和动画中断。
- Niagara 用于弹体、命中、范围爆发和控制效果。
- Gameplay Cue 可用于与 GAS 效果关联的表现，但不得把关键伤害规则只写在  
  Cue 中。
- 资源不足、技能冷却、命中和任务完成都应有明确反馈。

## 4.6 UI

V1.0 最小 UI：

- 玩家生命值条。
- 玩家法力值条。
- 三个技能与普通攻击的状态提示。
- 技能冷却或不可用提示。
- 当前任务名称与目标进度。
- 任务完成提示。

UI 只读取或订阅权威状态并显示结果。不要让 UI  
自己计算真实伤害、扣除法力或推进任务。

# 6. AI Agent 管控模式

## 6.1 角色定义

### 项目负责人（用户）

负责：

- 确认项目范围与优先级。
- 决定是否接受架构变更。
- 审查 Agent 的方案与风险说明。
- 在关键节点进行实际试玩与验收。
- 理解并能解释交付代码。
- 对外发布、作品集使用和资产许可承担最终确认责任。

### 主 Agent / 技术负责人 Agent

负责：

- 读取本策划案和开发状态文档。
- 检查工程实际状态。
- 把需求拆成小任务。
- 设计实现方案并明确受影响文件。
- 协调代码、蓝图、测试与文档工作。
- 汇总结果、阻塞问题和下一步建议。

### 执行 Agent

可按能力分工，例如：

- C++ 实现 Agent。
- UE 编辑器/蓝图操作 Agent。
- 测试与验证 Agent。
- 文档与资产登记 Agent。

如果平台不支持多个 Agent 协作，则由一个 Agent  
按不同职责阶段执行，不应假装存在实际并行能力。

## 6.2 Agent 的最高优先级规则

1. 先读项目文档、当前状态与相关代码，再行动。
2. 不把推测当作事实；无法验证时明确标注。
3. 不在未扫描的情况下重构整个工程。
4. 不删除、覆盖或批量重命名资产，除非任务明确授权且已有备份或可回滚提交。
5. 不修改与当前任务无关的文件。
6. 不自行引入新插件、第三方依赖或大型资源包。
7. 不将编译成功等同于功能正确。
8. 不将静态检查、代码阅读或编辑器截图冒充真实运行测试。
9. 不伪造测试结果、日志、文件路径、类名或资产引用。
10. 不在没有用户确认的情况下扩展项目范围。
11. 发现已有实现时优先复用；修改前说明为什么原实现不足。
12. 每次任务结束必须更新状态记录，并列出未完成项。

## 6.3 标准任务流程

每项任务都按以下流程执行：

### A. 读取与检查

- 读取  
  `ProjectBrief.md`、`DevelopmentStatus.md`、相关模块说明和近期任务记录。
- 检查 UE 版本、插件状态、工程文件和目标代码。
- 搜索相关类、资产、配置和调用链。
- 确认当前工程是否能编译，以及最近一次已知可运行版本。

### B. 提出实施计划

必须写明：

- 任务目标。
- 现状与证据。
- 预计修改的文件/资产。
- 不修改的范围。
- 实现方案与替代方案。
- 风险与回滚方式。
- 验收条件。
- 需要用户确认的事项。

低风险、范围明确的任务可以直接执行；涉及模块边界、数据格式、插件替换、批量资产迁移、删除或范围扩展时必须先请求确认。

### C. 执行最小改动

- 一次只完成一个可验收的功能单元。
- 先实现最小正确版本，再做优化。
- 尽量保持 diff 小且易审查。
- 不用自动化脚本批量改写未经检查的项目文件。
- 修改  
  `.uproject`、`.uplugin`、`Build.cs`、目标文件、资产重定向或项目配置时，要说明影响。

### D. 验证

根据改动类型选择：

- 静态代码审查。
- UBT/IDE 编译。
- 编辑器打开检查。
- PIE 或独立运行测试。
- 自动化测试。
- 手动验收清单。
- 日志与崩溃检查。

每项验证必须记录"通过 / 失败 / 未执行 /  
无法执行"，并附证据。未执行不得写通过。

### E. 汇报与交接

每次完成后输出：

1. 本次目标。
2. 修改内容与文件列表。
3. 核心设计决策。
4. 验证命令、操作步骤和结果。
5. 已知问题与风险。
6. 回滚方式。
7. 更新后的项目状态。
8. 下一项建议任务。

## 6.4 Agent 权限等级

---

等级                    可执行内容                                       是否需要预先确认

---

L0：只读                扫描文件、读取代码、分析日志、列出风险           通常不需要

L1：局部修改            单一功能的小范围代码或文档改动                   任务目标已确认即可

L2：工程配置            修改模块依赖、插件启用、输入配置、关键资产引用   必须先说明影响；重要变更需确认

L3：结构性变更          大规模重构、批量迁移、删除资产、替换框架         必须明确批准并准备回滚

L4：不可逆/外部动作     发布、上传、购买、签署许可、删除唯一副本         不允许 Agent  
自行执行，必须由负责人操作或明确授权

## 6.5 变更控制

以下事项属于重大变更：

- 更换 UE 小版本或升级项目版本。
- 更换 GAS 相关架构。
- 替换任务插件或修改其公共接口。
- 改变 ASC 的所有权与初始化策略。
- 批量修改资产路径或重命名资产。
- 新增需要额外许可或付费的资源。
- 引入联机、存档、装备等新系统。
- 调整本项目的核心范围或验收指标。

重大变更必须记录：原因、影响范围、备选方案、迁移步骤、测试计划、回滚方式和批准结果。

# 7. 文档与版本控制

## 7.1 必备文档

建议在项目根目录或 `Docs/` 下维护：

- `ProjectBrief.md`：项目目标与范围。
- `GameDesign.md`：游戏玩法与内容设计。
- `TechnicalDesign.md`：技术架构与模块职责。
- `DevelopmentStatus.md`：当前状态、已完成、进行中、阻塞项。
- `TaskBoard.md`：任务列表、优先级、依赖与状态。
- `DecisionLog.md`：关键技术决策及理由。
- `TestPlan.md`：测试策略与验收记录。
- `AssetRegister.md`：资产来源与许可。
- `AgentRules.md`：Agent 行为规范。
- `KnownIssues.md`：已知问题与临时解决方案。
- `Changelog.md`：版本变更记录。

本文档可作为初始 `GameDesign.md` 和 Agent  
执行基线；实际开始开发后，应将不同职责的内容拆分成独立文档，避免单一文档过度膨胀。

## 7.2 Git 规则

- 在开始修改之前检查工作区状态。
- 不覆盖用户未提交的改动。
- 重要里程碑前建立可回滚提交。
- 提交信息应说明实际改动，例如 `feat: add arcane bolt ability`。
- 不把 Derived Data  
  Cache、临时构建输出和可再生成文件无条件纳入版本控制。
- Unreal 项目常见的 `.uasset`、`.umap`  
  等二进制资产应根据项目协作方式合理纳入版本控制；不要误删。
- `.gitignore` 必须结合实际 UE 工程与团队工具检查。
- 每次提交前确认改动清单，不允许把无关文件混入提交。
- 不能只依赖 Agent 的记忆；当前真实文件和 Git 状态才是事实来源。

## 7.3 状态文件格式

`DevelopmentStatus.md` 至少包含：

- 当前里程碑。
- 工程可编译状态与最后验证时间。
- 当前可运行状态。
- 已完成任务及证据。
- 正在进行的任务。
- 阻塞项。
- 已知缺陷。
- 当前 Git 提交。
- 下一步唯一优先任务。

# 8. 里程碑与任务分解

以下里程碑按依赖顺序排列。具体日期根据实际开发速度调整，不以日期压力跳过验收。

## M0：工程基线

### 目标

建立可重复打开、编译和运行的工程。

### 任务

- 确认 UE 版本、IDE、编译工具链与目标平台。
- 创建 C++ Third Person 工程。
- 确认模板角色移动、镜头、跳跃正常。
- 确认项目模块名、目标文件与插件状态。
- 建立 Git 仓库、`.gitignore` 和首个基线提交。
- 建立 Docs 文档目录。
- 建立开发日志与状态文件。
- 记录干净启动与编译流程。

### 验收

- 干净启动工程成功。
- C++ 编译成功。
- PIE 中角色移动与镜头正常。
- 基线提交可用于回滚。
- 所有实际环境信息已记录。

## M1：角色框架与输入

### 目标

在不破坏模板行为的前提下，建立项目自己的角色扩展点。

### 任务

- 盘点模板中现有 Character、Controller、GameMode 和输入类。
- 决定哪些类继承、哪些类保留。
- 建立项目角色类或扩展组件。
- 接入 Enhanced Input。
- 统一输入绑定生命周期。
- 为后续 ASC 初始化预留明确位置，但不提前写未验证的完整 GAS 流程。

### 验收

- 角色移动、镜头和跳跃仍正常。
- 输入无重复绑定。
- 工程可编译。
- 新增类的职责与继承关系有文档说明。

## M2：GAS 最小可用骨架

### 目标

确认 GAS 能在当前工程中正确初始化，并验证属性与效果链路。

### 任务

- 确认 GameplayAbilities、GameplayTags、GameplayTasks  
  等所需模块和插件状态。
- 盘点当前 UE 版本与 GAS API。
- 明确玩家与敌人的 ASC 所有权方案。
- 实现最小 AttributeSet。
- 建立属性初始化方式。
- 建立一个简单 GameplayEffect。
- 验证属性变化与 UI/日志观察路径。
- 验证初始化只发生一次。

### 验收

- 项目可编译和运行。
- ASC 可正确初始化。
- 属性可按预期变化。
- 不出现重复授予能力或重复初始化。
- 初始化方案及生命周期有说明。

## M3：伤害、死亡与普通攻击

### 目标

完成从玩家攻击到敌人死亡的完整链路。

### 任务

- 定义基础伤害规则。
- 实现普通奥术攻击。
- 确定弹体或命中检测方式。
- 统一伤害应用路径。
- 实现敌人生命值变化。
- 实现死亡状态和唯一死亡入口。
- 处理死亡后禁止继续攻击、移动或重复结算。
- 加入基础命中与死亡反馈。

### 验收

- 普通攻击能造成正确伤害。
- 同一次命中只结算一次。
- 敌人死亡后不会重复执行死亡逻辑。
- 伤害、死亡与表现分层清楚。
- 至少有一套可重复的测试步骤。

## M4：资源消耗、冷却与主动技能

### 目标

完成两项主动技能与一个终极技能的规则链路。

### 任务

- 实现法力消耗。
- 实现冷却。
- 实现奥术震荡。
- 实现霜缚。
- 实现星陨。
- 定义控制状态与解除规则。
- 加入失败反馈与技能状态 UI。
- 测试技能取消、资源不足、冷却中、目标死亡等情况。

### 验收

- 资源与冷却规则正确。
- 不能在资源不足或冷却中违规施放。
- 控制状态可正确结束。
- 技能范围与视觉反馈大体一致。
- 终极技能不会重复扣费或重复结算。

## M5：敌人 AI 与战斗场景

### 目标

让战斗从静态目标变为可重复游玩的遭遇战。

### 任务

- 建立基础敌人角色。
- 实现发现、追击、攻击和死亡行为。
- 根据需要配置导航与感知。
- 处理受控状态与 AI 行为的协调。
- 建立小型灰盒地图。
- 调整敌人数量、距离和战斗空间。

### 验收

- 敌人能在预期条件下发现并追击玩家。
- 玩家进入攻击范围后敌人能够攻击。
- 受控敌人能停止或限制正常行为。
- 敌人死亡后 AI 不再执行战斗行为。
- 地图可以从出生点完整游玩到战斗结束。

## M6：UI、任务插件与交互

### 目标

把战斗变成有明确目标和结果的游戏体验。

### 任务

- 实现 HUD 属性显示。
- 实现技能状态显示。
- 检查现有任务插件的公共接口与数据结构。
- 在独立测试环境验证任务生命周期与进度语义。
- 创建任务适配层。
- 将敌人死亡与任务进度接口连接。
- 按需要实现区域目标或交互目标。
- 实现任务完成提示。
- 验证重复死亡上报和多个目标匹配。

### 验收

- HUD 与实际属性一致。
- 击杀目标只在正式死亡后更新。
- 一次死亡不会重复推进任务。
- 多目标任务行为符合配置。
- 任务插件不直接控制伤害或敌人死亡。
- 插件接口和适配层职责有文档说明。

## M7：表现与 Demo 打磨

### 目标

提高可读性和展示质量，不改变已验证的核心规则。

### 任务

- 完善施法、受击和死亡动画。
- 加入弹体、命中、范围技能和控制特效。
- 加入基础音效。
- 优化 HUD 可读性。
- 调整战斗节奏、敌人数量与技能数值。
- 检查性能和日志噪声。
- 完成从启动到任务完成的完整演示流程。

### 验收

- 关键动作有清晰反馈。
- 不存在明显阻断体验的视觉或音频错误。
- Demo 可连续游玩。
- 关键演示流程可重复执行。

## M8：作品集与技术复盘

### 目标

把项目变成可展示、可解释、可验证的求职作品。

### 任务

- 记录关键技术决策。

- 录制短演示视频。
- 整理关键代码讲解。
- 编写已知限制与未来改进计划。

### 验收

# 10. 风险与应对

## 10.1 Agent 大规模改动导致工程损坏


**应对：** 小步修改、任务前检查 Git  
状态、里程碑提交、限制文件范围、重大重构先批准。

## 10.2 引擎版本或 GAS API 不一致

**应对：**  
以实际安装版本、头文件、模块配置和编译结果为准；使用官方文档核对  
API；不要直接复制其他 UE 版本代码。

## 10.3 C++ 与蓝图职责混乱

**应对：**  
每个功能明确权威逻辑所在位置；蓝图尽量配置与组合；避免双重写入状态。

## 10.4 资产不兼容或许可证不清楚

**应对：**  
导入前验证许可证、骨架、动画重定向、插件依赖和资源质量；在资产登记表中留档。

## 10.5 GAS 范围不断扩大

**应对：**  
先完成一个属性、一个效果、一个能力的纵向闭环，再扩展技能数量；不提前实现复杂网络、天赋或装备系统。

## 10.6 任务插件接口与战斗逻辑耦合

**应对：**  
使用适配层；战斗逻辑只报告已发生的玩法事实；插件不直接依赖具体敌人蓝图或技能类。

## 10.7 功能很多但没有可玩 Demo

**应对：**  
以里程碑验收控制范围；优先保证普通攻击、敌人死亡、任务更新和胜利反馈完整运行。

## 10.8 用户无法解释 Agent 生成的代码

**应对：**  
每个核心系统完成后安排简短代码复盘；项目负责人必须能解释类职责、调用链、关键状态和错误处理；必要时让  
Agent 用教学方式逐段讲解。

# 11. 资源策略

## 11.1 资源优先级

1. UE 第三人称模板提供的角色与基础功能。
2. 引擎自带或项目可合法使用的基础资源。
3. 官方资源渠道或可信免费资源。
4. 必要时再引入额外角色、动画、特效和音效包。

## 11.2 导入前检查

- 来源和许可证。
- 是否需要署名或限制商业使用。
- 是否依赖额外插件。
- 是否与当前 UE 版本兼容。
- 骨架、动画和材质兼容性。
- 资源是否超出当前里程碑需要。
- 导入后是否能干净删除或回滚。

## 11.3 资源选择原则

不要为了视觉效果一次性导入大量素材。先完成可玩灰盒，再针对最影响体验的环节补充资源。资源本身不是验收结果；只有被正确集成并经过运行验证的资源才算完成。

# 12. 开发规范与 Definition of Done

每个任务只有满足以下条件，才可标记为"完成"：

- 需求与验收条件明确。
- 修改范围与设计理由有记录。
- 代码符合现有工程风格。
- 不引入无关改动。
- 相关配置、资产与依赖正确。
- 编译结果已记录。
- 运行测试已执行，或明确标注无法执行及原因。
- 关键边界情况已检查。
- 相关文档已更新。
- 已知问题与后续工作已记录。
- 负责人能够理解核心实现。
- 如有必要，已创建可回滚提交。

状态定义：

- **Backlog：** 尚未开始。
- **Ready：** 需求、依赖与验收条件明确。
- **In Progress：** 正在实施。
- **Blocked：** 被依赖、环境或未决决策阻塞。
- **Implemented：** 已实现但尚未完整验证。
- **Verified：** 已按验收条件验证通过。
- **Done：** 实现、验证、文档与复盘均完成。

不能把 `Implemented` 直接等同于 `Done`。

# 15. 项目启动后的第一批任务

第一批任务应严格限制在工程准备与审计，不应立即生成整套 GAS 系统。

## AV-001：确认开发环境与工程基线

**目标：** 建立可编译、可运行、可回滚的第三人称 C++ 工程。

验收：

- UE 版本、IDE、编译工具链与目标平台已记录。
- 工程可编译和运行。
- 第三人称角色移动、镜头和跳跃正常。
- Git 基线已建立。
- `DevelopmentStatus.md` 已创建。

## AV-002：扫描模板架构

**目标：** 在修改前弄清现有模板提供了什么。

验收：

- 记录 Character、Controller、GameMode、输入配置等真实类名。
- 记录现有蓝图与 C++ 类之间的关系。
- 记录插件和模块依赖。
- 给出建议扩展点和风险。
- 不执行未经批准的重构。

## AV-003：建立项目技术骨架

**目标：** 根据 AV-002 的审计结果确定最小目录、命名与类扩展方案。

验收：

- 方案与实际工程结构一致。
- 说明哪些类保留、哪些类扩展、为什么。
- 新增文件范围明确。
- 修改后工程仍可编译和运行。

## AV-004：审计任务插件

**目标：** 先理解插件现状，决定如何验证和接入。

验收：

- 列出公共接口、核心类、数据结构与模块依赖。

- 设计最小测试矩阵。
- 明确增量上报、绝对进度同步、目标匹配和重复上报语义。
- 在负责人确认前不大规模重写插件。

## AV-005：建立 GAS 最小验证计划

**目标：** 在确定 ASC 初始化方案后，用最小样例验证属性和效果链路。

验收：

- API 与模块依赖经过当前 UE 版本核实。
- 设计仅包含必要类与必要资产。
- 明确初始化、属性变化和测试方式。
- 不在验证之前批量创建所有技能。

# 17. 最终原则

Arcane Vanguard 的目标不是让 AI Agent 一次性生成尽可能多的代码，而是让  
Agent 在受控、可审查、可验证的流程中持续交付真实可运行的功能。

项目负责人始终拥有最终决策权。Agent  
的实现建议不等于事实；代码已写入不等于功能已完成；编译通过不等于游戏逻辑正确；视觉效果存在不等于玩法闭环成立。

**最终成功标准：一个能稳定运行、可以完整游玩、技术架构清楚、关键功能经过验证，而且项目负责人能够独立解释的第三人称魔法战斗  
Demo。**
