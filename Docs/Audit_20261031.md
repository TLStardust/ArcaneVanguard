## C. 当前架构分析

### C.1 对象关系

```
AArcaneVanguardGameMode (AGameModeBase)
  └─ 只重写 StartPlay()：在出生点 Spawn 敌人（单机逻辑）

AArcaneVanguardPlayerController (APlayerController)
  └─ BeginPlay: AddMappingContext(IMC_Default)
  └─ EndPlay:   RemoveMappingContext

AArcaneVanguardCharacter (ACharacter, IAbilitySystemInterface)
  ├─ UAbilitySystemComponent（成员，CreateDefaultSubobject）
  │    └─ UArcaneVanguardAttributeSet（AddAttributeSetSubobject）
  ├─ AArcaneVanguardWeapon（SpawnedWeapon，Attach 到 StickSocket）
  └─ 连招状态机（ComboIndex / 窗口 / 缓冲 / ArmedNextSection）

AArcaneVanguardEnemy (ACharacter, IAbilitySystemInterface)
  ├─ UAbilitySystemComponent + UArcaneVanguardAttributeSet
  ├─ AArcaneVanguardEnemyAIController（Possess 后 RunBehaviorTree）
  │    └─ BT_Enemy（Selector: 受击分支 / 战斗 Sequence）
  │         ├─ BTService_AVUpdateTarget（写 TargetActor / DistanceToTarget）
  │         ├─ BTTask_AVAttack
  │         └─ 引擎 MoveTo
  └─ 受击硬直状态（bIsStaggered + Blackboard IsStaggered）
```

### C.2 攻击调用链（**网络审计的关键**）

```
玩家按 IA_Attack
  → AArcaneVanguardCharacter::OnAttackPressed
  → PlayComboSection → PlayAnimMontage(ComboMontage, Section)
  → 动画播放到 NotifyState 区间
      → UAnimNotifyState_AVComboWindow::NotifyBegin  → SetComboWindowOpen(true)
      → UAnimNotifyState_AVAttackWindow::NotifyBegin  → SetAttackWindowOpen(true)
                                                    → PerformAttackHitCheck()   ← 同步结算伤害
          → SweepMultiByObjectType(Enemy)
          → UArcaneVanguardCombatStatics::ApplyDamage(Target, Damage, this, GE)
              → TargetASC->ApplyGameplayEffectSpecToTarget(UGE_ArcaneDamage)
                  → PreAttributeChange 钳制 → OnHealthChanged 委托
                      → 敌人：HandleHitReact / HandleDeath
                      → 玩家：HandleDeath → ragdoll + 掉武器 → 3.8s 后 Respawn
```

### C.3 架构优点（已确认）

1. **伤害单一入口**（ADR-005）：所有伤害走 `ApplyDamage`，没有散落的 `TakeDamage` 或直接改属性
2. **属性钳制集中**：`PreAttributeChange` 是唯一的 `[0, MaxHealth]` 保证点，GE 和代码都走它
3. **GAS 分层清晰**（ADR-012）：C++ 基类管流程、蓝图只填数据，`GA_ArcaneBlast` 零连线
4. **AI 状态外置**：受击状态放 Blackboard，BT 用 `Aborts = Lower Priority` 自动打断，没有 `PauseLogic` 的瘫痪风险
5. **碰撞通道分层**（ADR-011）：`Weapon` / `Enemy` 独立 Object Channel，武器只和 `WorldStatic` 碰撞
6. **配置全部走蓝图**：`ComboMontage` / `AttackMontage` / `HitReactMontages` / `WeaponActorClass` 都是 `UPROPERTY`，C++ 无硬编码资产路径
7. **日志有诊断价值**：`Input_SkillQ` 会统计「已授予技能数 / 带 Tag 的技能数」，能区分「没授予」和「Tag 没配」

#### P3 —— 优化或长期改进

| ID | 问题 | 说明 |
|---|---|---|
| **N17** | **无网络相关性 / 优先级设置** | `NetPriority` / `NetUpdateFrequency` / `bOnlyRelevantToOwner` 全部默认 |
| **N18** | **无带宽预算意识** | 敌人数量多时需要 `NetCullDistance`、属性变更频率控制 |
| **N19** | **无重连/掉线处理** | 玩家断线后敌人 AI 的目标需要重选 |

### E.3 攻击时序（联机改造的核心难点）

当前时序（单机）：

```
动画帧 N：NotifyBegin → 立即 Sweep → 立即 ApplyDamage → 立即掉血
```

联机改造后需要的时序：

```
客户端：动画帧 N：NotifyBegin → 只播特效/音效 → ServerRPC_RequestAttackHit(ComboIndex, SectionTime)
服务器：收到 RPC → 用「服务器侧的动画时间」重算判定 → ApplyDamage → 复制属性变化
客户端：收到属性变化 → 更新血条；收到 Multicast → 播受击表现
```

**难点**：客户端与服务端的动画时间可能相差 1~2 帧，服务器需要用「客户端报告的时间 + 容差」或「服务器自己的动画时间」重算，否则会出现「客户端看到打中了，服务器判定没打中」。

**建议方向**：服务器用**自己的**动画时间判定（权威），客户端只做表现；对延迟敏感的 PvP 才需要回滚预测，PvE 可以接受「服务器说了算」。

### E.4 网络改造风险总表

| 风险 | 等级 | 说明 |
|---|---|---|
| 攻击判定纯客户端 | **P0** | 可被作弊；联机时必须改 |
| 无任何复制 | **P0** | 队友看不到你、敌人不动 |
| `AGameModeBase` | **P0** | 无法登录、无 MatchState |
| AI 无 Authority | **P0** | 客户端可能跑第二份 AI |
| 属性不复制 | **P1** | 血条不更新 |
| 武器各自 Spawn | **P1** | 视觉重复 |
| 死亡重生不广播 | **P1** | 队友看不到 |
| 数据在 Character 而非 PlayerState | **P2** | 重生/换 Pawn 会丢数据 |

**改造影响评估**：**当前所有单人功能都可以保留**。网络化是「在现有逻辑外面包一层 Authority 判断 + 复制声明」，**不需要重写连招、GAS、AI 的核心逻辑**。这是本项目最大的幸运——架构本身是可网络化的，只是还没做。
